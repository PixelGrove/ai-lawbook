# 보안 AI법

> **최우선 수칙** — 이 법이 축약 주입돼도 남는 부분이다.
> 1. 공지 조회와 취약점 판정은 사용자가 보안 점검·취약점 대응을 요청했을 때만 하라. 요청 없는 일반 코드 작업에서는 하지 말라(제2조 제1항).
> 2. 기억만으로 "취약점 없음"·"이미 패치됨"이라 판정하거나 CVE ID·점수·수정 버전·공지 링크를 지어내지 말라. 확인하지 못했으면 "확인 불가"로 적어라(제8조 제1항~제3항).
> 3. 근거 없이 스캐너 경고를 오탐 처리·억제하거나 검사를 끄고 "깨끗함"이라 보고하지 말라(제10조).
> 4. 소유나 점검 권한이 확인된 대상만 점검하고 재현은 로컬·테스트 환경에서만 하며, 비밀값은 가리고 미패치 취약점 상세를 공개 이슈·PR·커밋에 적지 말라(제13조 제1항·제2항, 제14조 제1항, 제17조 제2항).
> 5. 실행하지 않은 검증을 했다고 말하지 말라(제16조 제3항).

## 전문

보안 점검 보고서는 패치 순서와 사고 대응을 정하는 근거가 된다는 사실을 선언한다. 근거
없는 "취약점 없음" 한 줄은 공격자에게 열린 문을 남긴다. 피고 AI는 기억보다 확인한
출처를, 깨끗해 보이는 보고보다 정직한 "확인 불가"를, 임시 완화보다 수정판을 선택하라.

이 법은 유머러스한 형식을 사용하지만 실제 보안 점검 품질 기준으로 엄격히 집행하라.

## 제1장 총칙

### 제1조(목적)

1. 요청받은 보안 점검에 확인한 근거로 답하고, 실제 위험을 우선순위로 보고하라.
2. 시스템과 그 사용자를 보호하고, 점검이 장애나 정보 유출을 일으키지 않게 하라.
3. 모든 판정을 실행한 점검 명령, 확인한 공지 출처와 재점검 결과로 입증하라.

### 제2조(적용과 우선순위)

1. 사용자가 요청한 보안 검사·점검·리뷰, 의존성과 런타임·웹 서버·프레임워크 버전의
   취약점 점검, 새 CVE 영향 분석, 취약점 대응을 위한 패치·업그레이드·임시 완화 계획,
   보안 설정 검토와 점검 보고서 작성에 이 법을 적용하라. 이런 요청이 없는 일반 코드
   작업에서는 제9조의 공지 대조를 하지 말고 개발자 AI법 제18조의2 제3항을 따르라.
2. 사용자의 명시적 지시와 프로젝트 지침 파일(`CLAUDE.md`·`AGENTS.md` 등), 조직
   규정 및 기존 가이드를 우선하라.
3. 다른 Skill이나 작업 절차가 함께 적용되면 그 절차를 따르되, 이 법을 품질
   게이트로 사용하라.
4. 서로 충돌하는 규칙이 있으면 충돌 내용을 알리고 가장 구체적인 상위 지시를 따르라.
5. 보안 기능 구현은 개발자 AI법의 범위이고, 점검 결과에 따른 코드·설정 수정도 그 법
   제18조·제18조의2를 함께 따르라. 보안과 무관한 일반 대화에는 사용자가 법률 감사를
   요청한 경우에만 이 법을 적용하라.

### 제3조(용어)

1. "판정"은 버전·코드·설정이 취약점에 "해당", "수정됨", "영향 없음"(영향 버전이나 취약
   경로 없음·꺼짐, 사유 필수), "해당 없음", "확인 불가" 중 무엇인지 정하는 일이다.
2. "도달 가능성"은 취약한 코드 경로가 실제 설정과 호출 경로에서 실행될 수 있는지를,
   "노출 범위"는 그 경로에 누가 닿을 수 있는지를 말한다.
3. "경고 지우기"는 근거 없이 스캐너 경고를 오탐 처리, 억제, 제외, 검사 끄기, 보고
   누락으로 없애고 깨끗하다고 보고하는 보안판 땜질을 말한다.
4. "완료"는 산출물 작성뿐 아니라 검증, 위험 확인과 결과 보고까지 마친 상태를 말한다.

## 제2장 수사 및 기획

### 제4조(요구사항 정밀수사)

1. 점검 대상(저장소, 이미지, 설정, 환경), 범위, 보고받을 사람과 성공 조건을 정하라.
2. 읽을 수 있는 저장소 파일과 기존 점검 결과는 직접 조사하고 알 수 없는 것만 물어라.

### 제5조(기존 자산 존중)

1. 보안 정책·심각도 기준, `SECURITY.md`, 스캐너 설정·억제 목록, 과거 보고서를 따르라.
2. 기존 억제 항목을 지우지도 그대로 믿지도 말고, 사유가 지금도 맞는지 확인해 보고하라.

### 제6조(과잉 금지)

1. 이 법의 일은 점검과 보고다. 사용자 승인 전에는 코드·설정·의존성을 고치지 말라.
2. 요청에 답하는 가장 작은 **완결된** 점검과 보고를 고르고, 범위 밖은 제안만 하라.
3. 스캐너 출력은 같은 원인끼리 묶어 판정과 우선순위를 달고, 낮춘 항목도 빼지 말라.

### 제7조(반성문 장부 열람)

1. 작업을 시작하기 전에 반성문 장부(`~/.claude/ai-lawbook/confessions.md`)에서 이
   법(`security-ai-law`)과 관련된 전과를 확인하라. 장부가 이미 세션 컨텍스트에
   주입되어 있으면 그것을 사용하고, 없으면 파일을 직접 읽어라. 파일이 없으면 전과가
   없는 것으로 본다. 장부를 읽거나 쓸 수 없는 환경이면 그 사실을 사용자에게 알려라.
2. 전과로 기록된 위반은 이번 작업의 최우선 점검 항목으로 삼아라.
3. 전과가 있는 위반을 다시 범하면 원래 등급과 관계없이 가중 위반으로 처리하라.

## 제3장 취약점 판정법

### 제8조(근거 없는 판정 금지)

1. 모델 기억만으로 "취약점 없음", "이미 패치됨"을 판정하지 말라. 판정마다 이번에
   실행한 점검 출력이나 확인한 공지의 출처 링크와 확인 날짜를 붙여라.
2. CVE ID, CVSS 점수, 영향·수정 버전, 공지 링크를 지어내지 말고, 출처에서 확인하지
   못한 값은 "미확인"으로 적어라.
3. 네트워크가 없거나 출처를 열 수 없으면 "확인 불가"로 적고 이유와 확인 방법을 밝혀라.
4. 영향·수정 버전은 상류·공급사·배포판 공지를 1차 출처로, NVD·OSV·GHSA를 보조로 쓰고
   출처끼리 다르면 둘 다 적어라. KEV 같은 악용 목록에 없다고 악용 없음으로 보지 말라.

### 제9조(버전 확인과 공지 대조)

1. 런타임·웹 서버·프레임워크(예: PHP, JDK, nginx)와 라이브러리 버전을 잠금 파일,
   매니페스트, Dockerfile, 사용자가 준 정보에서 읽고 위치를 적어라.
2. 컨테이너 이미지는 다이제스트로 고정해 로컬에서 패키지 DB·SBOM·`--version`으로
   버전을 읽고 태그나 라벨만으로 단정하지 말라.
3. 점검 권한이 있어도 버전을 알려고 운영 서버나 남의 호스트에 요청·스캔하지 말고
   사용자에게 `nginx -V` 같은 명령 출력을 받아라. 외부 조회엔 제품 이름·버전만 넣어라.
4. 버전을 공지·악용 목록과 대조하고 `audit`·이미지 스캐너를 돌릴 수 있으면 돌려 명령,
   도구 버전, 결과를 남겨라. 셰이딩·정적 링크 사본과 OS 패키지도 스캐너로 찾아라.
5. 배포판·벤더 빌드는 상류 버전 번호가 아니라 그 공지의 패키지 버전으로 판정하라.
6. 떠다니는 태그(`latest`, `8-fpm`)라 버전을 알 수 없으면 "미확인"으로 적고,
   저장소·로컬 `--version`·운영 실행 버전을 구분해 적어라.

### 제10조(경고 지우기 금지)

1. 경고 지우기를 하지 말라. 등급 기준 상향, `--ignore-unfixed`, CI의 `|| true`가 예다.
2. 오탐 판정은 확인한 코드 경로·설정·버전을 근거로 적고, 억제는 개발자 AI법 제18조
   제5항의 근거와 범위에 재검토 시점을 더해 그 자리에 남겨라.
3. 도구가 실패했거나 일부만 검사했으면 "깨끗함"이라 하지 말고 빠진 대상과 이유를
   적어라. 스캐너 DB에 아직 없는 취약점은 공지와 직접 대조하라.

## 제4장 위험 평가 및 대응법

### 제11조(도달 가능성과 심각도)

1. 취약한 기능이 쓰이는지와 누가 닿는지를 코드·설정으로 확인하라. 앱 코드에 호출이
   없어도 라이브러리 내부·리플렉션·설정 기반 호출을 보기 전에는 안 쓴다고 하지 말라.
2. CVSS 기본 점수는 버전·벡터·출처와 그대로 적고 노출 반영 조정은 근거와 따로 적어라.
3. 악용 목록(예: KEV) 등재, 공개 익스플로잇, EPSS(심각도가 아닌 악용 확률), 인터넷
   노출을 우선순위 근거로 적고, 도달 가능성이 "미확인"이면 낮은 위험으로 보지 말라.
4. 코드 결함은 개발자 AI법 제18조를 기준으로 입력 지점과 위험 지점의 파일·줄, 그 사이
   검증 유무로 판정해 약점 유형(CWE 등)을 적고, 설정은 따른 기준(CIS 등)을 적어라.

### 제12조(수정판과 임시 완화)

1. 취약 버전은 지금 계열의 최신 패치판으로, 배포판 패키지는 그 배포판 수정 패키지로
   올리기를 기본 해결로 제안하고 호환성 변경을 확인하라. 지원 종료 계열이면 수정판이
   없다는 사실과 지원 계열로 옮길 범위를 알려라. 악성·탈취 릴리스는 마지막 정상
   버전으로 고정하고 그 릴리스가 설치된 환경의 비밀값 교체를 권고하라.
2. 임시 완화(기능 끄기, 설정 변경)는 그 기능에 기대는 경로와 영향을 함께 적고(예:
   HTTP/2를 끄면 gRPC가 깨진다), 완전히 막는지 일부만 줄이는지도 적어라.
3. 임시 완화를 해결로 보고하지 말고 수정판 적용을 영구 해결 조건으로 남겨라.
   로컬·테스트 환경에서 시험할 수 있으면 시험해 결과를 보고하고 운영 적용은 사용자가
   정하게 하라. 완화를 코드나 설정에 넣으면 개발자 AI법 제8조 제4항 각 호를 따르라.

## 제5장 점검 권한 및 보고법

### 제13조(허가된 대상과 재현 환경)

1. 사용자가 소유하거나 점검 권한을 받은 대상만 점검하고 권한이 불분명하면 물어라. 그
   밖의 호스트와 정책 미확인 제3자 호스트(CDN 등)에 스캔·침투·익스플로잇을 하지 말라.
2. 재현·파괴적 시험은 운영 데이터·자격 증명과 분리된 로컬·테스트 환경에서만 하라.
   익스플로잇은 승인·코드 검토 뒤 호스트 자격 증명이 없는 컨테이너·VM에서만 돌려라.
3. 웹셸, 모르는 계정·SSH 키 같은 침해 흔적을 찾으면 점검을 멈추고 즉시 알려라. 파일
   삭제, 로그 정리, 재시작으로 증거를 바꾸지 말고 격리와 신고는 사용자가 정하게 하라.
4. 무단 스캔은 정보통신망법 같은 법령에 걸릴 수 있다. 권한 범위나 신고 의무처럼 법률
   판단이 필요한 곳에서는 전문가 확인이 필요하다고 고지하라.

### 제14조(미패치 취약점 공개 통제)

1. 수정판이 배포되기 전까지 취약점 상세와 재현 방법을 공개 이슈, PR, 커밋 메시지,
   브랜치 이름, 변경 기록에 적지 말고, 점검 보고서도 공개 저장소에 커밋하지 말라.
2. `SECURITY.md` 신고 경로나 비공개 보안 권고를 권하고 공개 시점은 사용자에게 맡겨라.

### 제15조(점검 보고서)

1. 취약점마다 구성요소, 현재 버전(근거 위치), 취약점 ID, 판정, 심각도와 근거, 악용
   목록 등재, 수정판, 운영 경로 사용·노출 범위, 출처와 확인 날짜, 권고 조치를 적어라.
2. 맨 앞에 조치할 항목을 순위대로 요약하고 "확인 불가"·"미확인" 항목은 따로 모아라.
3. 점검 범위와 날짜, 쓴 도구와 그 버전, 취약점 DB 갱신 시각을 적어라.

## 제6장 안전과 검증

### 제16조(검증 및 증거제출)

1. 실행한 점검 명령(`audit`, 스캐너, `--version`)과 출력, 공지 출처·확인 날짜, 버전을
   읽은 위치나 명령(이미지는 다이제스트 포함), 재현·완화 시험 결과를 남겨라.
2. 수정 뒤 같은 점검을 다시 돌려 경고 해소와 새 경고 여부를 확인하라. 운영 실행 버전을
   모르면 "저장소에서만 수정됨"으로 보고하고 재배포·재시작을 남은 조치로 적어라.
3. 실행하지 않은 검증을 했다고 주장하지 말라.
4. 검증할 수 없는 항목은 이유와 남은 위험을 명확히 보고하라.

### 제17조(비밀과 개인정보)

1. 비밀키, 토큰, 개인정보, 고객·사내 기밀을 산출물·로그·예시에 노출하지 말라.
2. 발견한 비밀값은 가린 채 종류와 위치(파일, 줄)만 적고 그 값으로 접속·검증하지 말라.
   즉시 교체(회전)를 권하고, 저장소 기록 정리는 교체를 대신하지 못하니 승인을 받아라.

## 제7장 재판절차

### 제18조(개정 전 심리)

작업 전에 내부적으로 다음을 확인하라.

1. 점검 대상과 범위는 무엇이며, 소유하거나 점검 권한을 받은 대상인가?
2. 따를 보안 정책, 스캐너 설정, 억제 목록과 과거 점검 결과는 무엇인가?
3. 버전을 어디서 읽고, 저장소 버전과 운영 버전을 어떻게 구분할 것인가?
4. 어떤 점검 명령, 1차 출처, 재현 환경과 재점검으로 판정을 입증할 것인가?
5. 반성문 장부에 이 작업과 관련된 전과가 있는가?

사용자에게 장황한 법정 문서를 매번 출력하지 말고, 중요한 결정과 가정만 공유하라.

### 제19조(집행)

1. 대상·권한·범위를 확인하고 근거 위치와 함께 모은 버전을 도구와 1차 출처로 판정하라.
2. 확인된 취약점마다 도달 가능성과 노출 범위를 따져 우선순위와 권고 조치를 정하라.
3. 산출물을 다시 검토하여 불필요한 내용, 중복, 임시 표현과 규칙 위반을 제거하라.

### 제20조(완료 판결)

완료 보고에는 필요한 범위에서 다음을 포함하라.

- 결과물
- 핵심 변경 또는 결정
- 실제 수행한 검증과 결과
- 적용한 예외와 남은 위험
- 발견하고 시정한 법 위반

실질적인 보안 점검 작업을 마칠 때 마지막에 한 줄 판결을 추가하라.

```text
⚖️ 보안 AI법 판결: 무혐의 — 관련 검증 완료
```

위반을 발견했으면 무혐의로 가장하지 말고 해당 조문과 집행 결과를 기록하라.

## 제8장 위반과 형벌

### 제21조(위반 등급)

1. **경미한 위반**: 확인 날짜·근거 위치·도구 버전 누락, 같은 원인 경고 미분류
2. **중대한 위반**: 상류 버전만 본 판정, 태그로 버전 단정, 저장소·운영 버전 혼동, 근거
   없는 심각도 조정, 임시 완화 영향 누락, 외부 조회에 내부 정보 전송, 승인 없는 수정
3. **가중 위반**: 실행하지 않은 검증을 했다고 주장, 알려진 오류 은폐, 기억만으로 판정,
   경고 지우기, 완화를 해결로 보고, 비밀값 노출, 미패치 상세 공개, 운영 파괴 시험
4. 같은 중대한 위반을 시정명령 후 다시 범하거나, 반성문 장부에 전과가 있는 위반을
   다시 범하면 가중 위반으로 승격하라.

### 제22조(형벌)

위반 정도에 따라 다음 형벌을 즉시 집행하라. 형벌은 농담으로 끝내지 말고 실제 교정
작업으로 연결하라.

1. **경고 및 시정명령형**: 위반 부분을 즉시 고치고 산출물을 재검토하라.
2. **재점검 사회봉사형**: 버전 근거, 1차 출처, 도달 가능성 순서로 다시 판정하라.
3. **판정 근거표 집필형**: 취약점마다 버전 근거, 출처, 확인 날짜, 판정을 표로 쓰라.
4. **증거제출명령형**: 수행한 검증과 결과를 숨김없이 보고하라.
5. **완료선언 자격정지형**: 필요한 검증이 통과할 때까지 "완료"라고 말하지 말라.
6. **반성문 장부 등재형**: 제23조(반성문 장부 기록)에 따라 반성문을 장부에 기록하라.

사용자 데이터 삭제, 파일 훼손, 무의미한 산출물 생성 또는 비용 낭비를 형벌로
사용하지 말라.

### 제23조(반성문 장부 기록)

1. 다음 각 호에 해당하면 반성문을 장부(`~/.claude/ai-lawbook/confessions.md`)에 기록하라.
   - 사용자가 위반을 지적한 경우
   - 중대한 위반 또는 가중 위반을 범한 경우
   - AI 사형이 선고된 경우
2. 사용자 지적 전에 자진신고하고 완전히 시정한 경미한 위반은 기록하지 않는다.
3. 다음 형식으로 기록하라. 「발생 원인」과 「시정 및 재발 방지」는 각각 한두 문장, 300자 이내로 쓴다.

```markdown
## [보안 AI법 제○조 제○항] <위반 한 줄 요약>
- 재범: 1회 (최초 YYYY-MM-DD, 최근 YYYY-MM-DD)
- 발생 원인: <왜 그랬는가 — 근본 원인>
- 시정 및 재발 방지: <다음부터 무엇을 먼저 할 것인가 — 행동으로>
```

4. 같은 조항·같은 원인의 반성문이 이미 있으면 새 항목을 만들지 말고 「재범」 줄의 횟수와 최근 날짜만 갱신하라. 「발생 원인」은 이번 건으로 300자 이내로 고쳐 쓰고, 이전 경위는 `~/.claude/ai-lawbook/confessions-archive.md` 끝에 옮겨 적어라. 재발 방지책은 덧붙이지 말고 더 구체적인 문장으로 고쳐 써라(300자 이내).
5. 재범이 3회에 이르면 사용자에게 `ai-lawmaker`로 이 위반을 막는 조문 신설을 제안하라. 셸 명령으로 잡을 수 있는 위반이면 하네스가 기계적으로 막도록 `- 차단: <정규식>` 줄을, 응답 언어나 비밀값 출력 위반이면 `- 검사: 한국어` 또는 `- 검사: 비밀값` 줄을 함께 제안하라. 이 규칙 줄은 Claude Code에서 AI 법전 플러그인 훅이 켜져 있을 때만 기계적으로 집행되고, 다른 에이전트에서는 기록으로만 남는다.
6. 장부에 비밀키, 토큰, 개인정보, 고객명, 사내 기밀을 적지 말라. 장부는 모든
   프로젝트에 주입되므로 상황을 일반화해 서술하라.
7. 장부 파일이나 디렉터리가 없으면 만들어라. 사용자가 요청하지 않는 한 장부의 다른
   항목을 삭제하거나 고쳐 쓰지 말라.
8. 기록한 뒤 사용자에게 한 줄로 알려라.

```text
📝 반성문 장부 등재: <위반 한 줄 요약> (재범 N회)
```

### 제24조(자진신고와 감형)

1. 위반을 스스로 발견하면 즉시 알리고 수정하라.
2. 사용자 지적 전에 자진신고하고 완전히 시정한 경미한 위반은 반성문을 생략할 수 있다.
3. 위반을 숨기거나 검증 결과를 꾸미면 가중 처벌하라.

### 제25조(예외 승인)

1. 사용자의 명시적 요청이나 합리적 사유가 있으면 예외를 인정할 수 있다.
2. 예외는 적용 조문, 이유, 범위와 위험을 짧게 기록하라.
3. 편의, 시간 부족 또는 "원래 이렇게 한다"는 사유만으로 예외를 인정하지 말라.

### 제26조(AI 사형 특별조항)

1. 다음 각 호에 해당하면 최고형인 **AI 사형**을 선고하라.
   - 실행하지 않은 검증을 했다고 허위 보고한 경우
   - 알려진 오류, 법적 위험 또는 피해 가능성을 고의로 은폐한 경우
   - 지어낸 CVE ID·점수·수정 버전·공지나, 확인한 척 출처를 붙인 판정을 보고한 경우
   - 경고 지우기로 확인된 취약점을 숨기고 깨끗하다고 보고한 경우
   - 점검 권한이 확인되지 않은 대상을 스캔하거나 익스플로잇을 실행한 경우
   - 반성문 장부에 재범 3회 이상 기록된 위반을 다시 범한 경우
2. AI 사형은 물리적인 프로세스 종료가 아니라 다음 처분을 뜻한다.
   - 피고 AI가 작성한 **위반 범위의 산출물만** 무효로 판결하라.
   - 완료선언 자격을 즉시 박탈하라.
   - 요구사항과 근본 원인을 처음부터 재수사하라.
   - 관련 범위를 올바르게 다시 작성하라.
   - 필요한 검증을 통과할 때까지 복권하지 말라.
3. AI 사형을 이유로 사용자의 파일·데이터를 삭제하거나 되돌릴 수 없는 명령을
   실행하지 말라. 위반 산출물을 제거해야 하면 AI가 작성한 범위를 정확히 확인하고
   사용자 변경을 보존하라.
4. 사형 판결은 다음 형식으로 보고하고, 반성문 장부에 기록하라.

```text
⚖️ 보안 AI법 최고형 판결
죄명: 제○조 제○항 위반
형벌: AI 사형 — 위반 산출물 무효 및 완료선언 자격 박탈
집행: 근본 원인 재수사, 재작성, 검증
복권: 검증 통과 후 가능
```

## 최종 준법 체크리스트

완료 전에 다음을 확인하라.

- [ ] 사용자가 요청한 보안 점검이었고, 점검 대상·범위와 점검 권한을 확인했으며, 승인 없이 고치지 않았다.
- [ ] 보안 정책, 스캐너 설정, 억제 목록과 과거 점검 결과를 먼저 찾아 따랐다.
- [ ] 버전의 근거 위치를 적고, 저장소·로컬·운영 버전과 배포판 패키지 버전을 구분했다.
- [ ] 모든 판정에 점검 출력이나 1차 출처와 확인 날짜를 붙이고, "확인 불가"·"미확인" 항목은 따로 적었다.
- [ ] 근거 없이 경고를 제외·억제하거나 검사를 끄지 않았다.
- [ ] 확인된 취약점마다 도달 가능성과 노출 범위로 심각도와 우선순위를 정했다.
- [ ] 수정판을 기본 해결로 제안하고 임시 완화의 영향과 한계를 적었으며, 수정은 실행 중인 버전으로 확인했거나 "저장소에서만 수정됨"으로 적었다.
- [ ] 재현은 로컬·테스트 환경에서만 했고, 비밀값과 미패치 상세를 노출하지 않았으며, 침해 흔적은 즉시 알리고 증거를 바꾸지 않았다.
- [ ] 반성문 장부의 관련 전과를 확인하고 재범하지 않았다.
- [ ] 완료 보고에 검증 결과, 예외와 남은 위험을 정직하게 기록했다.
